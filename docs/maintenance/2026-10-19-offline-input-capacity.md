# 离线联系输入容量修复

## 现象与范围

用户截图显示“离线联系资料超过容量（16位私聊角色、64 KiB资料）”。源码有三处共用容量错误：私聊查询超过16条直接拒绝、已确认角色字段超过读取上限拒绝、最终 JSON 超过64 KiB拒绝。后续准备成功也未主动清除先前的准备错误。截图本身不能区分触发了哪一处；本轮分别处理这些路径。

用户已批准优化，并单独批准仓库外临时合成数据／模拟服务的隔离回归。没有真实存档、凭据、模型、已安装应用或安装器操作，没有新一轮 Git 推送／发布授权。

## 实现

- 每批最多16位角色，按私聊稳定标识保存轮选位置；正常在线记录保持该批次，真实离线恢复后为下次准备后续候选。每次最多检查64条关联，整批无效时允许后续本地准备继续轮选。
- 仅投影已确认角色的性格、描述和背景，SQL 按字节读取前缀；按实际 UTF-8 和 JSON 转义计算本次参考预算，保留来源标识。原角色卡、世界书、聊天不修改，不调用模型压缩资料。
- 完整快照仍遵守 SQLite 的64 KiB约束，公共背景与已有意图只使用剩余空间。单个坏候选隔离；公共背景不可用时不以私密资料补位。
- 准备问题与模型任务失败分别提示。后续准备成功可清除旧准备错误；实际失败／中断回执保留，未重新排队。旧快照字段兼容，投递前来源版本、身份、状态和新消息校验继续有效。
- DTO 新增可选的准备统计字段，前端契约由生成器同步。无需数据库迁移；每次恢复的模型任务数量与最多一条消息规则保持。

源码入口：`application/offline_contact_inputs.py`、`persistence/offline_contact.py`、`SqlAlchemyDirectorStore.approved_persona`、`BackgroundTaskFeedback.tsx`。

Python 使用仓库外临时 SQLite 与合成角色，前端使用模拟服务和内存 DOM；分别隔离 APPDATA／LOCALAPPDATA、缓存、模型离线环境与临时目录。

首次隔离回归发现新字节投影将空字符串经 SQLite `substr(empty BLOB)` 转成 NULL，导致有效角色被排除；已在文本类型判断内用空 BLOB 补值，保留非文本拒绝，随后复核通过。另有一条 Starlette／AnyIO 既有弃用提示，不影响结果。
