# 主动联系与未读消息（2026-10-04，用户已明确要求）

0.1.29 前只有离线补消息；本方案实现在线联系、同事由双人联系，以及在线/离线共用的等待回复门禁。2026-10-18用户明确更新投递与回应规则：只复用恰好两位角色的群，否则分别私聊；任一私聊回复回应整次共同邀请。以下现行规则替代首版自动建群及逐会话等待规则，不另行要求重复审批。

- 在线默认关闭，当前世界/玩家单独同意后台用量。复用已有 Director 活动与有界模型网关；不另调 API 抽签。最短间隔默认 360 世界分钟，可设 15～1440；首次开启建立新基线，不补发过去在线联系。
- 只有当前有效的真实 rest/leisure 才能作为单人联系理由；双人必须是 Kernel 已开始的同一次共同休闲，双方仍在同地点/活动中。每个日常 plan 最多发起一次在线联系。允许没有联系。
- 双人共用一个目的、地点和活动，各发一条独立可理解的台词。优先投递当前世界／玩家已有的未解散群，角色成员必须恰好为这两人；多个合格群稳定选择一个。没有则分别投到双方既有私聊，不自动建群、不使用含其他角色的群。两条台词同一次生成，目的／地点须匹配已核验事实，全部检查后原子入库。共同在商场休闲可自然邀玩家来逛街；未发生／未获授权的不同事由和第三名角色不得混入。回答只是聊天，不自动移动玩家／接受行动。
- 联系领取、生成和送达期间均占用门禁。在线和离线跨角色共用门禁；单人或群聊联系需本玩家在原会话里保存更晚的回复。分别私聊的两条共同邀请以同一个episode关联，任意一条私聊回复即可解除整次等待，其他无关会话不计入。不复制回复，不清除另一条未读；阅读、刷新、开关与重启都不解除。
- 只有双方获准角色资料、当前共同事实与逐条公开背景参与后台生成；不发送私聊、摘要、私人记忆或隐藏世界书。迟到结果重新检查身份、资料、授权、活动和门禁。失败/中断不自动付费重放。
- 通用未读使用持久会话阅读位置，与是否回复分开。角色消息使对应私聊/群聊和聊天导航显示红点；只在前台可见会话确认已加载的位置，不把未加载新消息标已读。旧聊天在升级时建立基线，保留原离线未读。
- 0.1.30 修复阅读确认：前台窗口中可见的消息直接提交其位置，不把另一个用于在线状态的 Core/Tauri 往返作为阅读前置；写入失败有界重试并显式提示，用户可手动重试。确认成功后重新读取未读快照；阅读仍不释放等待回复门禁。
- 0.1.31 将离线恢复的跳过原因细分：有未回复的主动联系时明确提示回原会话回复；有其他在线/离线联系占用门禁时提示处理中。同一离线理由已处理和未回复并存时优先提示未回复。只改变本次恢复的状态诊断，不补发、不解除门禁、不增加模型调用；旧版笼统状态仍可读取。
- 增量迁移 0035 保持旧结构校验。构建/静态检查不代表真实存档升级或模型体验验收；测试仍由用户负责。

复用调查见 `docs/research/2026-10-04-proactive-contact-reuse.md`。当前公开接口维持 API protocol 1，新增独立路由。首次在线开启仍在界面明确后台费用。

## 双私聊投递的实现边界（2026-10-18）

- 沿用锁文件中的SQLAlchemy 2.0.54（MIT）、既有SQLite写事务与JSON字段；不新增依赖或服务。参考[SQLAlchemy事务](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html)与[SQLite JSON函数](https://www.sqlite.org/json1.html)，不引入额外消息队列或流程框架。
- 复用既有群成员查询和每角色私聊映射，投递前再核验活动／身份／资料／门禁。只选未解散且恰好两位角色的群；无合格群时，两条私聊、各自turn／dispatch／消息位置和邀请来源在同一事务提交，第二条失败全部回滚。
- 两条私聊仍共用一次生成及一次episode。现有episode JSON仅追加两个投递turn的ID供门禁关联，不复制回复或私聊正文；其大小在模型调用前预留。没有新增表／列／迁移，也不改写历史episode。
- 门禁只用该episode列出的两个投递及当前玩家更晚的已保存回复判断；没有关联字段的旧单人／群聊／离线消息沿原规则处理。独立未读位置不随另一会话回复清除，过去的未回复联系不批量解锁。
- 本轮只做静态、格式／类型、Python语法与SQL表达式编译及文档／隐私核对，不添加或运行自动测试、应用或模型，不操作真实存档；源码尚未构建发布，真实送达／回复／重启仍待验收。

## 0.1.35 开启设置保存修复

源码确认两处适配问题：configureProactiveContact 缺少application/json请求头；FastAPI将JSON解析为dict再validate_python，而strict=True的expected_player_id: UUID不接受正常JSON字符串。客户端补齐请求头，仅该UUID字段使用Field(strict=False)作标准UUID校验，开关、间隔、版本等字段仍严格校验，玩家一致性和revision并发门禁保留。复用已有Pydantic能力，不自写解析器；依据[Pydantic UUID文档](https://docs.pydantic.dev/latest/api/standard_library_types/#uuid)及[严格模式字段覆盖](https://docs.pydantic.dev/latest/concepts/strict_mode/)。

页面读取未完成不再显示为未开启；保存失败不会被自动刷新清除，成功收到核心保存结果后明确显示已保存，身份/模型/校验失败分别提示。只修设置适配，不改变已有存档开关、不自动启用或重放模型调用；启动恢复只将writing标为attention，不设置enabled=False。0.1.34提交没有改Core/开关逻辑；没有读取真实存档，因此不声称核实了用户以前的保存值。

用户验收：退出托盘旧程序，打开0.1.35配套包，在原世界/原玩家点击同意开启，确认已开启并保存；刷新、切页、正常退出重开应仍为开启。保存状态和实际发出邀请分开验收，仍需自动活动、许可、间隔、真实理由及无未回复联系。不由工程端运行测试或调用模型。
