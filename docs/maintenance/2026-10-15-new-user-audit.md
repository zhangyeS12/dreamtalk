## 1. 授权与检查方法

用户明确允许本轮使用独立临时用户目录运行自动化检查、新用户界面体验、临时 Core／前端及本机模拟模型响应。本轮只使用合成世界、虚构角色、生成的纯色 PNG 和内存假密钥；没有读取真实存档、系统凭据或既有 API 配置，没有调用外部模型、产生模型费用或修改开机启动／系统设置。

使用 `webapp-testing` 技能，以全新浏览器配置运行无界面的 Edge／Playwright。浏览器、Python 和 Node 限制外部连接；模型请求只发往临时环回 HTTP 服务。界面连接真实 Core，模型配置保存由模拟桌面桥接线，Rust 配置更新另由使用内存凭据库的既有测试核对。

因此：界面与 Core 的实际结果可以作为这条隔离链路的证据；模拟的 Tauri 凭据／原生状态，不能当成 Windows 凭据管理器、托盘、自启动、安装器或更新安装成功的证据。启动失败测试使用模拟的宿主失败回执，并结合真实 Rust 处理路径确认；配置损坏和备份恢复使用真实 Core／存储实现及临时文件。

## 2. 发现的问题

### A-01 · P1 · 合法快照在恢复阶段失败

入口：书架／设置 → 数据与备份 → 恢复所选备份。

根因位于 [save_safety.py](../../services/core/src/livingworld/infrastructure/save_safety.py) 的 `quarantine_restored_tasks()`，727–735 行。该函数对包括 `world_news_batches` 在内的多张表统一执行：

```sql
UPDATE world_news_batches
SET state='interrupted', error='save_restored'
WHERE state IN ('queued','dispatched')
```

但 [WorldNewsBatchRecord](../../services/core/src/livingworld/infrastructure/persistence/story_models.py)（92–114 行）没有 `error` 列。SQLite 即使没有匹配的任务，也会在解析这条语句时失败。因此，从未启用世界动态的普通存档同样受影响。

本轮实际步骤：在临时世界建立角色和两条聊天消息、导入三库表情；通过维护屏障创建快照；完整校验快照成功；将其复制到另一临时应用目录；调用真实 `restore()`。结果为 `sqlite3.OperationalError: no such column: error`。临时恢复目标的稳定 ID 摘要保持不变，失败发生在替换当前数据之前；原快照仍通过校验。

影响：能看到和校验备份，不等于能够恢复。当前包含该表的完整快照恢复被阻断，首个阻断之后的恢复步骤尚未完整跑通。没有证据表明这次错误意味着用户的真实数据已经丢失。

修复方向：按各任务表的真实结构隔离恢复任务，保留既有费用记录和不自动重发约束；不能删除整段隔离逻辑来绕过错误。修复后需覆盖空任务表、在途任务、已完成任务及恢复前后原数据保留。

### A-02 · P1 · 模型配置异常后无法在页面内重新配置 API

入口：书架 → 模型设置，或世界内 → 设置 → 模型与聊天。

[ModelSetup.tsx](../../apps/web/src/ModelSetup.tsx) 第244行要求 `status !== "degraded"` 才显示编辑表单。配置格式损坏时，Core 会保留世界功能并报告 `degraded`，见 [llm_runtime.py](../../services/core/src/livingworld/bootstrap/llm_runtime.py) 的异常降级分支。原生端 [lib.rs](../../apps/desktop/src-tauri/src/lib.rs) 的 `managed_chat_model_setup`、配置创建／更新也各自要求可解析的受管理配置，并没有异常配置的修复路径。

实际复现：只破坏临时目录中的模型配置并重新启动临时 Core。书架和已有世界仍能显示，模型设置显示“模型配置或凭据状态异常”，但模型输入框和保存按钮数量均为0。随后已恢复临时配置。没有读写真实配置。

影响：用户不能通过重新填写 API 修复异常，会被迫修改文件或寻求工程协助。这违反新确认的普通用户免维护要求。

修复方向：提供保留原异常配置的明确修复入口，允许重新配置当前作用域的模型，并保护其他世界、原凭据和数据。需同时处理前端可操作性与后端契约；只去掉前端条件不够。凭据存储不可用与配置文件损坏应分别处理。

### A-03 · P2 · 启动失败后的“重新打开”不会重新启动 Core

[App.tsx](../../apps/web/src/App.tsx) 第30–49行的重试只重置 React 状态并再次执行发现流程；[lib.rs](../../apps/desktop/src-tauri/src/lib.rs) 第222–242行的 `core_connection` 遇到宿主 `Failed` 直接返回 `core_failed`。已有更新恢复命令仅适用于相应升级交接，不是首次启动的一般恢复路径。

模拟宿主返回 `core_failed` 后，点击“重新打开”仍停在同一错误页；记录到重复发现请求，没有发起 Core 重启命令。Rust 源码也确认该行为。前端15秒超时与宿主30秒启动窗口另存在不一致，慢启动可能先被前端判失败；后一个时序风险本轮未单独动态测量。

影响：一次暂时的启动失败也需要用户退出整个应用再开；按钮名称和实际能力不一致。

修复方向：通过宿主提供受控、有限、可重复点击而不并发重启的恢复操作，协调启动窗口；保留存档屏障，不重放生成任务。不能让普通用户结束进程或处理端口。

### A-04 · P2 · API 密钥无效的确定原因被丢弃

兼容适配器 [openai_compatible.py](../../services/core/src/livingworld/infrastructure/llm/openai_compatible.py) 第339–340行已将401／403识别为 `LLMErrorCode.AUTHENTICATION`。但 [chat_reply.py](../../services/core/src/livingworld/application/chat_reply.py) 第137–149行的 `_generation_error()` 除结构化输出错误外，统一转换成 `chat_generation_failed`；[chatFeedback.ts](../../apps/web/src/chatFeedback.ts) 第41行因此只显示通用失败。

实际复现：本机模拟服务明确返回401与 `invalid_api_key`，界面显示“这轮回复未完成。消息已保存。生成服务未能完成这次回复……”，没有说明需要更新密钥，也没有到当前世界模型设置的操作入口。该次模拟记录为一次服务请求，无自动重试；玩家消息保留。

影响：只会配置 API 的用户无法区分密钥错误、余额／限流和服务临时故障，可能反复发送新消息。

修复方向：传递安全、有限的错误分类，给出原因和对应设置入口；不要把供应商原始响应、密钥或完整请求直接显示／记录，也不要增加后台探测或自动重发。

### A-05 · P2 · 未收录模型的首次配置仍要求技术知识

[ModelSetup.tsx](../../apps/web/src/ModelSetup.tsx) 第114–148行使用已核对预设或手填容量。实际体验中，只填写未收录的兼容服务地址、模型 ID 和密钥，点击保存会被要求打开高级设置并自行查找输入容量；填写后才能完成后续流程。

这属于新确认的普通用户要求下的体验缺口，不是可信 Token 上界门禁本身有错。不能为了简化表单而猜测容量、取消预算或要求用户虚填较小值。

修复方向：扩大有可靠来源的供应商／模型预设与明确的匹配引导；无法确定时给出普通用户能理解的缺项和路径，避免再让用户计算容量与整轮额度。超出已核对信息的自动发现／能力声明应另行明确契约。

### A-06 · P2 · 既有回归检查与当前功能已明显不同步

本轮保留并原样运行既有测试，没有弱化或修改断言。结果：

| 检查 | 本轮结果 |
| --- | --- |
| Python 既有完整套件 | 1694通过、30失败、1警告；490.26秒 |
| 前端既有 Vitest | 24通过、34失败；6个测试文件失败；7个未处理错误 |
| Rust 桌面底层测试 | 11通过、0失败；使用临时目录和内存凭据库 |
| ESLint 与 TypeScript | `npm run lint`通过，包含 `tsc --noEmit` |

已追踪的失败包括：

- 前端 jsdom 缺少 `matchMedia`，旧 client mock 缺少 `socialSnapshot`／`replyRecovery` 等方法，部分断言仍使用旧页面和接口。
- Python 组合根假对象缺少 `token_bounder`；旧聊天假上下文不是当前容量打包器要求的 JSON，导致未进入被测业务分支就失败。
- 若干旧迁移测试在只升级到历史 revision 后调用最新 ORM，提前访问当时不存在的 `removed_at`；另有测试拼出空列 `SELECT FROM`，或将 FTS 无 `rowid` 的内部表当普通表导出。
- HTTP 精确字段断言未同步媒体／观测字段；固定33条上下文断言未同步按容量装配；旧公共背景测试使用非常驻关键词条目，却要求未命中关键词的 `hello` 也激活。
- 架构断言既有确定性 `uuid5` 被一概禁止等过时规则，也有应用层使用 Pydantic 与现有依赖禁令不一致的实际维护问题，应逐项确认，而不是整体放宽架构保护。

这些失败不能当成“64个真实用户功能故障”，也不能笼统说全部无关紧要。尤其新备份恢复故障没有被现有测试挡住。后续应先恢复与当前契约一致的有效检查，再补本轮已复现故障的回归覆盖，保留权限、费用、幂等和恢复不自动重发的断言。

- 没有安装／卸载程序、执行真实应用内更新或回退，没有改 Windows 注册表、自启动和系统凭据。真实更新成败仍需安全的独立 Windows 环境覆盖，不能由本次模拟桌面桥或编译通过替代。
