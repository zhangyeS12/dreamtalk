# LivingWorld 产品原则

## 状态与解释方式

Stage 0 文档，功能尚未实现。冻结规则的唯一原文清单见 [PRODUCT_SPEC.md](PRODUCT_SPEC.md)。本文把相关规则归为产品审阅主题，不引入额外冻结要求。未明确的行为见该文档的待确认问题清单。

## 1. 世界持续存在，角色在世界中行动

**冻结依据：FR-01、FR-02、FR-03、FR-06。**

LivingWorld 的产品定位是持久化、事件驱动的多角色 AI 世界。Director 负责世界与宏观剧情调度，Character Agent 主要负责自己拥有的记忆、人格表达和与玩家对话。玩家在任意时刻只能存在于一个物理地点。

**概念解释：** 世界调度与角色表达是不同责任。Director 改变世界，但不能直接替 Character Agent 编写最终对玩家台词。远程私聊与群聊允许跨地点进行，消息不改变玩家物理位置；对话数量不能被当作玩家具有多个物理位置的依据。新创建的本地玩家默认从所在世界的“家”开始。

## 2. 事实存在与参与者知情分别建模

**冻结依据：FR-04、FR-05、FR-07。**

世界真实事实、Character Knowledge 和 Player Knowledge 分离。后台已发生但玩家不知道的事件不能直接展示给玩家。关系在后台存在，不能向普通玩家展示数值。

**概念解释：** “已经发生”“某个角色知道”“玩家知道”是三个不同判断。角色得知事件不意味着玩家同时得知；关系变化也不等于向普通玩家开放数值。知识获得途径和非数值关系表达的形式尚未冻结。

## 3. 主动联系尊重玩家状态和联系理由

**冻结依据：FR-08、FR-09、FR-10、FR-11、FR-12。**

Busy 时不允许 Director 发起非必要主动联系；Available 时允许 Director 安排单角色或一组角色主动联系。“可以安排”不是每次变为 Available 都必须联系。

同一个理由最多主动发送一次，玩家未回复不能持续催促。多角色主动联系围绕统一目的组织为 Outreach Episode。

**待确认边界：** 必要联系的定义、理由去重作用域、Episode 内多角色消息的组织方式及生命周期均待确认，不能从“一组角色”推导出各角色可以重复使用相同理由独立催促。

## 4. 批量规划与程序执行分工

**冻结依据：FR-13、FR-14、FR-15。**

Director 使用批量 World Plan + Event Reservoir。传统程序负责候选事件的激活、延期或取消；不能为每个普通小事件单独调用 LLM。只有 Planning Window 耗尽或大量计划失效才触发 Replan。

**概念解释：** `CandidateEvent != WorldEvent`。候选事件只有被激活后才成为真正的世界事实；计划文本和候选池的存在不等于其中的事情已经发生。

**待确认边界：** Planning Window 的具体含义、耗尽条件及“大量失效”的判断口径尚未确定；本原则不预设调用频率、算法或技术栈。

## 5. 生成内容先形成草稿，再预览与提交

**冻结依据：FR-17、FR-18、FR-19、FR-20。**

AI Character Builder 和 AI World Builder 可以联网研究并生成带来源的 Draft。自动生成内容必须经过 Draft → Preview → Commit。产品要求支持 Character Card V2/V3、PNG/JSON 和 Lorebook 导入。

**概念解释：** 来源用于说明生成内容的依据，不能仅因联网研究或生成成功就把草稿当作已提交的世界内容。导入内容的预览、确认和兼容策略仍待定义；不在此擅自将所有导入都定义为自动生成。

**已确认的聊天边界：** Character Agent 的运行时台词经系统校验后直接发送，无需逐条由用户预览确认；自动生成的持久创作内容仍须 Draft → Preview → Commit。

**待确认边界：** World Plan、事件生成和记忆摘要如何适用三阶段流程，见 P-16；上述聊天决定不等于对这些内容作豁免。

## 6. 面向普通用户，同时支持配置和诊断

**冻结依据：FR-16、FR-21、FR-23。**

产品具有用户可配置的 Director 风格面板。UI 面向非技术用户，高级模型参数隐藏到 Advanced/Developer Settings。Developer Mode 能查看 Director、Agent、Memory、LLM 使用等决策 Trace。

**待确认边界：** 风格项、设置结构和诊断访问范围尚未确定；Developer Mode 的存在本身不授予绕过未知事件展示约束的权限。

## 7. 世界分支与资源使用进入产品定义

**冻结依据：FR-22、FR-24。**

世界支持 Checkpoint 与 Timeline Branch。产品记录 Token、Latency 和 Cost，并支持预算与模型路由。

**待确认边界：** 分支与恢复范围、成本统计口径、预算耗尽行为及模型路由策略待确认。本阶段不承诺回滚已产生的模型费用或已发生的外部交付。

## 文档审阅检查

- 需求描述是否明确区分冻结规则、概念解释、待确认问题和实现状态？
- 是否把候选事件误写成已发生事实，把角色知识误写成玩家知识，或把关系数值暴露给普通玩家？
- 是否把 Director 的调度权扩展为直接编写最终角色台词？
- 是否违反玩家唯一物理地点、Busy 限制、同理由最多一次或统一目的 Episode 的规则？
- 是否绕过批量规划、程序激活或 Draft → Preview → Commit？
- 是否把待调研技术、未确定阈值或未实现功能写成既成事实？

这份检查表用于审阅文档，不表示已经建立自动测试、运行时约束或功能实现。
