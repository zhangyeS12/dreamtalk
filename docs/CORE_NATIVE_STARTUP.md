# Core全页读取卡住修复（桌面0.1.23）

## 确认的现象与证据

用户运行的路径是0.1.22 generation-read-fix完整目录，Core与桌面进程仍在，窗口能操作但全部读取失败。最新日志已到core_ready/credential_sync_complete；本地不带凭据的/system/live在4秒内没有响应，CPU长期停在2.65625秒。

用临时py-spy0.4.1只抓线程栈，没有使用--locals，也没有保存进程内存转储。MainThread停在线程池submit → 新线程start → 等待启动事件；asyncio_0停在历史语义检索_decode → NumPy导入 → multiarray原生模块初始化；控制管道线程在阻塞读stdin。这比“模型回复慢”或“旧版自启动”更具体：主线程被堵住，HTTP与3秒超时回调也无法执行。

NumPy上游#24290报告了Windows管道子进程的stdin读取线程与首次NumPy导入同时存在时卡住的条件。现场栈和本项目启动顺序与该模式一致；未采集原生DLL内部栈，不能声称已经直接验证了某个CRT/loader锁。

## 实现

Core在数据库/工作线程及桌面stdin监听器启动之前，在启动线程准备NumPy和FastEmbed的原生库。只导入库，不加载模型、不推理、不读取缓存/历史或联网。完成/失败写固定安全日志native_runtime_ready/native_runtime_unavailable。导入失败则本次Core使用关键词检索，不在控制管道启动后重新尝试该原生导入。

语义模型仍首次需要时在工作线程中创建，3秒等待及关键词回退保留。桌面启动发现期由12秒调整为30秒，给预加载留出时间；不是调整聊天/付费请求的等待或自动重试策略。没有新依赖、存档结构、API合同、外发范围或背景费用变化。

## 更新与验收

从旧程序托盘“退出并停止后台运行”，再运行完整0.1.23目录；若旧Core无法正常退出，原监督器会按既有退出流程处理，更新时不要删存档或拆换Core。使用自启动时在新版显式保存启动位置。

先打开通讯录/聊天并发送一条消息，再切换页面和刷新记录，检查所有本地读取继续响应。长短期记忆仍保留；本轮没有清空缓存或关闭语义检索来掩盖问题。若仍卡住，记录新版发生时间，继续通过安全日志与只读栈定位。

源码与构建检查不代表真实存档和模型聊天已验收。临时空目录冷启动诊断的授权与结果单独记录在HANDOFF；不复用以前的一次性诊断授权。
