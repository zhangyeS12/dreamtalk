# dreamtalk 用户流程

## 状态与阅读约定

以下流程记录已确认的产品职责与信息边界；其中部分能力已实现，具体进度见根目录 README 和相应架构文档。冻结规则编号和待确认问题编号均引用 [PRODUCT_SPEC.md](PRODUCT_SPEC.md)。

除冻结规则要求的顺序外，流程组织用于解释需求，不构成新增的产品决策。需要进一步决策的分支明确标为“待确认”。

P-16 已部分明确：Character Agent 的运行时聊天台词经系统校验后直接发送；自动生成的持久创作内容仍需 Draft → Preview → Commit。World Plan、事件生成和记忆摘要的具体边界仍待确认；后文未重复写出三阶段流程的步骤，不代表相关内容已获豁免。

## 当前前端入口（2026-10-02）

首页为横向世界档案书架。每本书代表一个真实世界，空白书位只用于创建；选择只预览，点击进入后显示四个业务入口。世界书的创建／联网生成／导入／编辑移动到书架管理；角色卡保留在世界内设置，原三阶段确认与隐藏／公共边界不变。返回书架不暂停世界，预览不计世界在线。三张图片封面留待后续。初始不选书也不显示右侧内容，悬停轻抽、点击完整抽出后才出现详情；空白书点击后再显示创建／导入入口，切换或取消归位。见[世界档案库](../WORLD_ARCHIVE.md)。

## F-01：研究并建立角色内容

**依据：FR-17、FR-19。**

1. 用户提出希望研究的角色。
2. AI Character Builder 可以联网研究角色，生成带来源的角色 Draft。
3. 内容进入 Preview，使待提交的内容和来源可供审阅。
4. 内容经过 Commit，完成 Draft → Preview → Commit 的必经过程。

**信息边界：** 生成 Draft 本身不等于已提交；联网资料也不自动成为某个角色或玩家拥有的知识。

**待确认：** 来源粒度、冲突处理、编辑与确认权限、Preview 具体内容，以及 Commit 的生效范围（P-06、P-10）。

## F-02：研究并建立世界内容

**依据：FR-18、FR-19。**

1. 用户提出希望研究的作品或世界。
2. AI World Builder 可以联网研究作品/世界，生成带来源的 World Draft。
3. 内容进入 Preview。
4. 内容经过 Commit，完成 Draft → Preview → Commit 的必经过程。

**信息边界：** 世界素材的来源、已提交内容、世界运行中已发生的事件以及玩家获知的信息不是同一概念。

**待确认：** World Draft 包含哪些内容、与已有世界冲突时如何处理、由谁确认 Commit、何时成为正式世界事实，以及玩家在创建世界时所见内容与 Player Knowledge 的关系（P-06、P-10）。

## F-03：导入角色卡与 Lorebook

**依据：FR-20；涉及自动生成内容时适用 FR-19。**

1. 用户提供 Character Card V2/V3、PNG/JSON 或 Lorebook 导入内容。
2. 产品识别与解释可支持的内容，并进入后续导入处理流程；具体处理和用户确认步骤待确认。
3. 若处理过程中自动生成内容，该内容必须经过 Draft → Preview → Commit。

**信息边界：** 支持导入不等于所有格式特性和扩展都已承诺兼容，也不等于导入文本全部成为玩家已知事实。

**待确认：** 格式兼容范围、来源缺失、不支持内容、冲突与重复导入的处理，以及是否对所有导入统一采用 Draft → Preview → Commit（P-06、P-11）。

## F-04：进入世界、互动与获知事件

**依据：FR-02、FR-03、FR-04、FR-05、FR-06、FR-07。**

1. 玩家在世界中拥有一个物理地点；任意时刻不能同时位于多个物理地点。
2. Director 调度时间、地点、世界事件、角色活动、角色相遇、关系变化和宏观剧情。
3. 玩家从当前世界通讯录打开角色聊天；首次打开时才建立或复用对应运行时 Character。跨地点私聊或群聊不改变玩家物理位置。
4. 玩家与角色互动时，Character Agent 负责自己拥有的记忆、人格表达和与玩家对话；Director 不直接替 Character Agent 编写最终对玩家台词。
5. 区分 WorldTruth、Character Knowledge 和 Player Knowledge，按玩家知情边界判断可呈现的信息。
6. 后台已发生但玩家不知道的事件不能直接展示给玩家；后台关系数值不能展示给普通玩家。
7. 聊天页置顶“世界事件”入口。点开后按世界时间及稳定账本顺序浏览当前世界、当前本地用户所绑定 Player 已获知的事件；切换世界时同步切换事件范围。它用于扩展聊天话题，不是全知公告。
8. 玩家可从已获知事件选择已有私聊或群聊，将事件标题作为待编辑消息带入会话；由玩家决定是否发送。该操作不授予角色对事件的知识，也不生成新的世界事件。

**概念示例：** 某角色在玩家不在场时参加会面。会面已发生，并不意味着玩家知道；角色之后通过对话传达有关内容是否以及如何形成玩家知识，需要按知识获得规则定义。

**已确认：** 新创建的本地玩家默认从当前世界的“家”开始；跨地点的私聊和群聊不改变玩家的物理位置。聊天是角色扮演的主体验；聊天页置顶的“世界事件”用于提供玩家已知的情境和话题，不是全知公告。

**待确认：** 移动与地点层级、知识获得和纠错、非数值关系表达，以及 Mission 的玩家体验（P-06、P-07、P-08、P-14）。

## F-09：私聊与群聊轮次

**已确认边界：** 私聊和群聊都是角色扮演对话。每个世界的联系人、角色卡和世界书内容彼此独立；当前世界的内容更新经预览确认后只影响该世界。通用玩家自我描述与世界专属身份分别提供给上下文，发生冲突时使用世界专属身份。

1. 玩家打开一个或多个当前世界联系人开始私聊或群聊；群聊参与者共享一份按序对话记录。
2. 一条玩家消息开启一个有限轮次；独立群聊调度器按角色性格和共享对话选择下一位发言者。玩家 `@` 某个群成员时，该角色先发言。
3. Director 不负责选群聊发言者；它继续负责批量世界计划。群聊调度器不提交世界事件，也不编写最终台词。
4. 一轮设有输入与输出 Token 总上限。选人、角色回复、路由回退和所有物理重试都计入；在每次物理调用前先保守预留输入并为输出留额度，不能可信预留时不调用模型。达到额度后不开始下一位发言。
5. 校验通过的角色台词直接发送。持久创作内容仍经过 Draft → Preview → Commit。

详细职责、信息边界及额度语义见 [聊天模型](../architecture/CHAT_MODEL.md)。

## F-05：Busy / Available 与主动联系

**依据：FR-08、FR-09、FR-10、FR-11、FR-12。**

1. 玩家在设置中手动切换 Busy / Available 状态。
2. Busy 时，Director 不得发起非必要主动联系。“必要”的定义与判定方式待确认，不能自行把剧情推进都归为必要联系。
3. Available 时，Director 可以安排一个角色或一组角色主动联系；Available 不表示必须立即收到联系。
4. 任何主动联系均受同理由最多主动发送一次的约束。
5. 多角色主动联系必须围绕统一目的，形成 Outreach Episode。
6. 最终对玩家的角色台词由 Character Agent 负责，Director 负责调度联系目的和参与安排。
7. 玩家未回复时，不能持续催促。

**概念示例：** 多个角色为同一次邀请参与主动联系时，统一组织为一个 Outreach Episode。不能仅因换了一个参与角色，就把同一邀请理由当作新的催促机会。

**待确认：** 必要联系边界、理由判重范围、一次主动发送如何对应多角色消息、重试语义、Episode 结束、玩家回复后的后续互动和并发 Episode（P-02、P-03、P-04）。

## F-06：配置 Director 风格

**依据：FR-16、FR-21；配置仍受其他冻结规则约束。**

1. 用户通过风格面板配置 Director 风格。
2. 产品以面向非技术用户的方式呈现相关概念。
3. 高级模型参数隐藏到 Advanced/Developer Settings。

**信息边界：** 可配置风格不改变 Busy 限制、未知事件不可直接展示、同理由最多一次或其他冻结规则。

**待确认：** 风格维度、可调范围、默认值及配置变更对现有 World Plan 的生效方式（P-09）。

## F-07：Checkpoint 与 Timeline Branch

**依据：FR-22。**

1. 世界支持 Checkpoint，作为恢复和分支语义待细化的产品概念。
2. 世界支持 Timeline Branch，使分支世界进程能够被表达。
3. 用户如何创建、选择、恢复或切换 Checkpoint / Timeline 的具体流程待确认。

**信息边界：** 支持 Checkpoint 和分支不自动确定保存范围、复制语义、分支合并或重放行为。

**待确认：** 时钟、事实、知识、记忆、关系、计划、候选事件、Conversation、未完成 Outreach Episode、已发送联系记录的恢复与分支处理，以及真实费用和外部交付与恢复操作的关系（P-03、P-12、P-13）。

## F-08：查看诊断与管理模型资源

**依据：FR-21、FR-23、FR-24。**

1. Developer Mode 提供 Director、Agent、Memory、LLM 使用等决策 Trace 的查看能力。
2. 产品记录 Token、Latency 和 Cost。
3. 产品支持预算与模型路由；高级模型参数放入 Advanced/Developer Settings。

**信息边界：** 这些是未来能力要求，并未实现诊断面板、用量采集或模型调用。Trace 的存在不自动授予普通玩家查看未知世界事件或关系数值的权限。

**待确认：** Developer Mode 的访问边界、Trace 保留与展示范围、用量统计粒度、预算耗尽行为和模型路由失败时的处理（P-08、P-13、P-15）。

## 与后台规划的关系

上述流程涉及 Director 调度时，仍受 FR-13、FR-14、FR-15 约束：批量 World Plan + Event Reservoir，传统程序激活、延期或取消候选事件，Planning Window 耗尽或大量计划失效才触发 Replan。不能把每次用户操作或每个普通小事件都定义为一次 LLM 调用。

`CandidateEvent != WorldEvent`：候选事件只有被激活后才成为真正的世界事实。世界事实形成后，是否可向玩家展示仍须满足 Player Knowledge 边界。

具体概念边界见 [DIRECTOR_MODEL.md](../architecture/DIRECTOR_MODEL.md)、[EVENT_MODEL.md](../architecture/EVENT_MODEL.md) 和 [KNOWLEDGE_MODEL.md](../architecture/KNOWLEDGE_MODEL.md)。
