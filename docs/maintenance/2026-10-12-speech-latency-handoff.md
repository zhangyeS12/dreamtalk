## 先看当前结论

后续现场：当前0.1.60已运行，但0.1.58遗留服务占用默认端口并触发旧合成方式提示。用户明确允许空闲时结束两个已核对的旧进程；已完成并保留当前Desktop与Core。用户接下来在设置检查启动新版服务，完整声音与性能仍待验收，见[处理记录](2026-10-12-legacy-speech-service-stop.md)。此次文档更新不改变已交付包内快照。

用户早先反馈：界面显示“本地模型正在合成声音 · 第 1/1 段 · 已等待 68 秒”，认为等待过长。记录为**配音耗时待排查**，不是已确认卡死，也不是已经通过声音验收。

- `elapsed_seconds` 从 Core 登记任务、创建 live 状态时开始计时，包括连接、模型首次加载、文本处理与合成等；**68 秒不等于这一段纯推理用了 68 秒**。
- 第 1/1 段是上游 `gr_progress` 最近报告的文本合成段数，不是音频秒数、Token 数或完成百分比。服务还能回应状态查询，不证明 GPU 在持续推进。
- 当前反馈说明任务已被报告到合成阶段；仍缺少本次实际设备、各阶段时间、输出音频时长、是否成功保存和是否听到声音。
- 首次加载、文本／输出长度、自回归解码、设备或显存状态均是待区分因素，不能把任何一个直接写成已确认原因。前轮未读取用户运行日志或存档、未核对进程；本轮新证据见[诊断记录](2026-10-12-speech-diagnosis.md)。

这条反馈发生在交付0.1.58之后，前轮进程核对曾显示旧0.1.54；随后本轮已确认运行0.1.58并收到播放器失败截图，不能唯一判定早先68秒反馈时的版本。最新历史日志约43秒加载、50秒后续处理、93秒至服务端ready，存在长度上限警告；不据此推定用户听到了完整声音或新版已验收。

停止／切页／隐藏／失焦仅停止队列、等待与播放；不要为了排查延迟清除旧任务回执、重置额度或重发未知任务。声卡播放与模型生成是不同阶段。

## 下一位接手人先做什么

前轮授权仅文档；本轮新增日志／进程／GPU及有限任务元数据只读诊断许可，结果见上述新记录。以下继续步骤**不授权模型生成或存档修改**；工程端自动测试、应用／模型测试、真实存档诊断仍按 AGENTS 第 20 节取得具体授权，用户自行体验不受此限制。

1. 确认实际 EXE、Core 与可选桥接版本，当前设置的路线／地址，以及是否由应用持有服务；不要仅按桌面快捷方式名判断版本。不要重启正在合成的任务来测试启动速度。
2. 在获准范围内收集同一任务的脱敏证据：输入字数、参考音频时长、连接／加载／文本准备／自回归／后续声学生成／保存／播放各阶段耗时，以及 GPU 是否使用、利用率、显存和输出音频时长。不要记录完整台词、音源、密钥或私聊。
3. 区分冷启动与已有模型的后续新任务。0.1.60已增加加载、实际device／BF16、GPT／声学／声码器、输出时长和RTF的受控数字日志；日志接线存在，但尚未取得新版模型任务数据。界面继续显示总耗时和真实回调。
4. 若确认 GPU 路径正常，再核对上游自回归解码、beam 配置、长度警告与音频完整性；若实际设备是 CPU 或显存不足，先查环境和设备选择。每个判断须有对应证据，不猜原因。
5. 只有取得阶段数据和声音对比后，才讨论具体参数／加速路径的取舍。一个完成条件是同条件下记录冷／热任务耗时及音频时长，明确改善了哪一阶段，同时声音完整、角色映射正确、未多发生成请求；目前尚无可承诺的速度目标。
